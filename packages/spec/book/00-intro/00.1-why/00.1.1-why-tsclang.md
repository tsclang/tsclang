# 00.1.1 Зачем нужен TSClang

TypeScript — один из самых популярных языков в мире. Но у него есть фундаментальные ограничения, которые невозможно исправить внутри экосистемы JavaScript.

## Проблема 1: Runtime overhead

TypeScript компилируется в JavaScript. JavaScript выполняется в движке (V8, SpiderMonkey, JavaScriptCore). Движок — это слой между вашим кодом и процессором.

```typescript
function fibonacci(n: number): number {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}
```

Этот код на TypeScript:
- Проходит через JIT-компиляцию (V8 сначала интерпретирует, потом компилирует горячие пути)
- Тратит память на скрытые классы и inline-кэши
- Не может использовать конкретные типы — `number` всегда `f64`, даже если нужен `i32`
- GC останавливает мир для сборки мусора

На C тот же код компилируется в машинные инструкции напрямую. Нет движка, нет GC, нет hidden classes, нет JIT-разогрева.

## Проблема 2: Нет нативного кода

TypeScript не может:
- Работать с памятью напрямую (указатели, MMIO-регистры)
- Работать без операционной системы (bare metal, embedded)
- Достичь предсказуемой latency (GC pauses)
- Компилироваться в бинарник без рантайма

## Проблема 3: Один тип числа

В TypeScript есть только `number` — это `f64`. Нет `i8`, `u32`, `i64`, `f32`. Невозможно:
- Эффективно хранить массив байтов (каждый байт занимает 8 байт как f64)
- Работать с регистрами микроконтроллера (нужен u8, u16)
- Контролировать переполнение (integer overflow в JS — молчаливый баг)

## Что делает TSClang

TSClang решает все три проблемы одновременно:

1. **Компилируется в C** — нативный код, нет движка, нет GC
2. **Конкретные типы** — `i8`, `u32`, `f64`, `usize` — как в C, но с безопасностью
3. **Memory safety** — ownership и borrow checker, как в Rust, но без lifetime-аннотаций

При этом синтаксис — TypeScript. Не нужно учить новый язык. Нужно выучить новые правила (ownership, конкретные типы), но не новый синтаксис.
