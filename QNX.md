План проверки под QNX.

## Шаг 1: Получить официальный QNX SDK (SDP)

Для сборки под QNX нужен их родной тулчейн (компилятор qcc, который является оберткой над GCC, и системные заголовочные файлы).

   1. Зайди на официальный сайт BlackBerry QNX.
   2. Зарегистрируйся в секции QNX Developer Network и запроси Eval-лицензию (ознакомительную лицензию на 30–60 дней для разработчиков) или бесплатную Non-Commercial лицензию.
   3. Скачай и установи QNX Software Development Platform (SDP) (сейчас актуальны версии 7.1 или новейшая 8.0). Тулчейн ставится на твой хост (Windows или Linux).

## Шаг 2: Скомпилировать C-код через qcc

Компилятор QNX называется qcc. Чтобы собрать сгенерированный твоим компилятором Си-код под QNX, нужно сначала инициализировать переменные окружения, а затем вызвать компилятор с указанием целевой архитектуры.

Пример для Linux-хоста (в терминале):

```bash
# 1. Активируем окружение QNX (путь зависит от версии и места установки)
source /opt/qnx800/qnxsdp-env.sh

# 2. Компилируем под x86_64 (для проверки в эмуляторе на ПК)
qcc -Vgcc_ntox86_64 -o my_ts_program main.c

# 3. Или компилируем под ARM (если будешь шить в реальную плату, например, Raspberry Pi)
qcc -Vgcc_ntoaarch64le -o my_ts_program main.c
```

## Шаг 3: Проверить работу в эмуляторе (QEMU)

### Шаг 3.1: Подготовка образа QNX для QEMU

Когда ты скачиваешь образ QNX Target из Software Center, обычно он идет в формате .vmdk (для VMware) или .qcow2. Если у тебя на руках файл .vmdk, его нужно сконвертировать в родной для QEMU формат .qcow2:

```bash
qemu-img convert -f vmdk -O qcow2 qnx_target.vmdk qnx_target.qcow2
```

### Шаг 3.2: Запуск QNX в QEMU (Команда для старта)

Для проверки сгенерированного кода тебе нужна сеть, чтобы перекидывать бинарники с хоста внутрь эмулятора. Мы запустим QEMU с пробросом сетевого порта 22 (SSH) наружу.

Выполни команду на своем хосте (Linux/macOS/Windows):

```bash
qemu-system-x86_64 \
  -m 2G \
  -smp 2 \
  -drive file=qnx_target.qcow2,if=virtio \
  -net nic,model=virtio \
  -net user,hostfwd=tcp::2222-:22 \
  -nographic
```

Разбор флагов, критичных для системщика:

* -m 2G -smp 2 — выделяем QNX 2 ГБ оперативной памяти и 2 ядра процессора.
* if=virtio и model=virtio — используем ультрабыстрые виртуальные драйверы ввода-вывода. QNX из коробки имеет современные драйверы virtio-blk и virtio-net (через службу io-pkt), так что диски и сеть взлетят мгновенно.
* hostfwd=tcp::2222-:22 — самая важная магия. Порт 22 (SSH) внутри QNX пробрасывается на порт 2222 твоего локального компьютера.
* -nographic — отключает тяжелое графическое окно QEMU. QNX загрузится прямо в текстовую консоль твоего текущего терминала.

### Шаг 3.3: Перенос и запуск твоего Си-кода

После того как QNX загрузится в консоли QEMU и попросит логин/пароль (по умолчанию обычно root без пароля или root / qnx), не закрывай этот терминал.

Открой второе окно терминала на своем хост-компьютере и выполни следующие действия:

## 1. Компиляция кода (повторим команду qcc)

```bash
source /opt/qnx800/qnxsdp-env.sh
qcc -Vgcc_ntox86_64 -o ts_app main.c
```

## 2. Закидываем бинарник в QEMU через наш проброшенный порт 2222

```bash
scp -P 2222 ts_app root@localhost:/root/
```

(Система спросит пароль от root внутри QNX, введи его).

## 3. Запуск и отладка

Теперь возвращайся в первое окно терминала (где запущена QNX внутри QEMU) или подключись туда по SSH:

```bash
ssh -p 2222 root@localhost
```

Внутри QNX выполняем:

```bash
cd /root
chmod +x ts_app
./ts_app
```

## Бонус для автора ЯП: Автоматизация тестов (CI/CD)

Поскольку QEMU управляется из консоли, ты можешь написать простой bash-скрипт для тестирования компилятора TSClang:

   1. Скрипт компилирует .ts в .c, затем через qcc собирает бинарник под QNX.
   2. Запускает QEMU в бэкграунде (-daemonize).
   3. Через scp закидывает бинарник, через ssh запускает его, считывает вывод (выхлоп console.log) и проверяет, совпадает ли результат с ожидаемым.
   4. Тушит QEMU одной командой.

Это позволит тебе гарантировать, что ни одно обновление твоей модели владения или асинхронных стейт-машин не сломает работу программы в реальной Hard RTOS среде.
